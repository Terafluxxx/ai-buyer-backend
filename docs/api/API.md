# AI Закупщик — документация REST API

Версия контракта: **1.0.0-draft**, 25.10.2026. Статус: предлагаемый контракт для согласования командой и параллельной разработки. Реализация сервера в поставку не входит.

Основной машиночитаемый файл: `openapi.yaml` (OpenAPI 3.0.3). Этот документ задаёт бизнес-правила, которые нельзя полностью выразить схемами. При изменении контракта оба файла обновляются вместе. Несогласованное расхождение блокирует интеграцию, а не разрешается догадкой разработчика.

## 1. Основание и границы MVP

Источник: «ИС2 (1).pdf»: диаграммы процессов на стр. 2, C4 на стр. 3, ER на стр. 4, функциональные требования на стр. 5–7, нефункциональные на стр. 8–9, ADR на стр. 10–11. Нумерация — страницы PDF.

Из источника сохранены: JWT, изоляция организаций, товары, складские остатки, продажи, предложения поставщиков, четыре вида CSV-импорта, расчёт показателей и рекомендаций, Dashboard, создание закупок и пять статусов. Архитектура: Vue.js + TypeScript, Java 21 + Spring Boot, PostgreSQL, модульный монолит. Интеграции с 1С, МойСклад и маркетплейсами не входят в MVP. Название AI не означает обязательную интеграцию с LLM: текущие рекомендации формируются детерминированными формулами.

## 2. Общие правила HTTP и данных

- Базовый путь: `/api/v1`. Локально: `http://localhost:8080/api/v1`; production: HTTPS на домене проекта.
- Запросы и ответы: `application/json; charset=utf-8`. Исключение — `POST /imports`, `multipart/form-data`. У 204 тела нет.
- Защита всех операций, кроме регистрации и входа: `Authorization: Bearer <accessToken>`.
- JSON-поля — camelCase; enum чувствительны к регистру. Неизвестные поля и невалидные query-параметры отклоняются. Пустое значение query не равно отсутствующему.
- ID — **строки**, хотя в БД BIGINT: `"101"`. Сервер дополнительно проверяет диапазон 1…9223372036854775807. Это исключает потерю точности JavaScript.
- Денежные суммы — строки с двумя десятичными знаками: `"1250.00"`. Диапазон 0.00…999999999999.99. Сервер считает через BigDecimal; клиент не вычисляет авторитетные итоги. Переполнение итогов: 422 NUMERIC_OVERFLOW.
- Расчётные дробные показатели — строки с четырьмя знаками, округление HALF_UP только при выводе. Целые quantities: 0…2147483647; в позиции закупки минимум 1. Суммарные счётчики могут быть int64; сервер не выдаёт значения выше безопасного для JS 9007199254740991, иначе 422 NUMERIC_OVERFLOW.
- Даты: `YYYY-MM-DD`; timestamps: RFC 3339, например `2026-10-25T10:00:00Z`.
- Строки trim на входе, кроме пароля. Пустые обязательные строки запрещены. SKU регистрозависим; email и ключ имени поставщика регистронезависимы. category — произвольная строка, не отдельный справочник.
- Все поля ответа обязательны согласно схемам, включая nullable. Неизвестные значения передаются `null`, списки — `[]`. В POST отсутствующие category/preferredSupplierId/recommendationId сохраняются как null.
- PATCH меняет только переданные поля. Поле можно очистить через null только если его схема nullable. PUT заменяет весь редактируемый состав ресурса, поля сервера не принимаются.
- Созданные версионируемые ресурсы имеют version=1. Успешное изменение повышает version на 1; одинаковое значение без изменения состояния оставляет её прежней. `version=0` допустима только для создания через upsert продаж/предложений. Несовпадение даёт 409 VERSION_CONFLICT. После конфликта фронт получает свежий ресурс и предлагает повторить изменение.
- `Location` при 201/202 содержит URI ресурса. Регистрация: `/api/v1/auth/me`; импорт: `/api/v1/imports/{id}`; пересчёт: `/api/v1/analytics/recalculations/{id}`.

### Пагинация

`page` начинается с 0, `size` по умолчанию 20, максимум 100. Ответ: `items`, `page`, `size`, `totalElements`, `totalPages`. `totalPages=ceil(totalElements/size)`, при пустом списке 0; страница за концом даёт 200 и `items: []`. Все фильтры объединяются через AND. Сортировка разрешена только из enum конкретного эндпоинта; общего произвольного sort нет. Если sort не предусмотрен, порядок указан в описании операции.

### Изоляция компании

companyId берётся из проверенного JWT, никогда из тела запроса клиента. Любой ID в пути, теле, фильтре, recommendationId, snapshotId и jobId проверяется в текущей компании. Чужой ресурс возвращает 404 RESOURCE_NOT_FOUND, как отсутствующий. Если указан несуществующий/чужой productId или supplierId в фильтре, также возвращается 404, а не данные другой компании. Обход проверки через вложенные items, CSV или join запрещён. Межтабличные связи проверяются на стороне сервера до изменения.

### JWT и выход

Предлагаемые настройки MVP: access JWT на 3600 секунд; refresh API отсутствует, после истечения нужен повторный вход. Claims: sub=userId, companyId, sid (UUID сессии), iat, exp, iss и aud. Проверяются подпись, разрешённый алгоритм, issuer, audience и срок; алгоритм развёртывания задаётся конфигурацией, а не заголовком клиента. Пароли хранятся BCrypt, 8–72 байта UTF-8 без обрезания. Хеши не возвращаются.

Logout сохраняет отзыв sid до exp в PostgreSQL; каждый защищённый запрос проверяет отзыв. Это общее постоянное хранилище, а не состояние в памяти одного инстанса. Фронт хранит accessToken в памяти, очищает его при logout/401; после перезагрузки страницы MVP требует вход. Нельзя обещать мгновенный logout, реализовав только удаление токена на клиенте. Ошибки login одинаковы для неизвестного email и неверного пароля. Для 429 сервер возвращает Retry-After в секундах; лимит конфигурируемый, фронт соблюдает заголовок.

### Идемпотентность POST

Обязательна для POST /purchases, /imports, /analytics/recalculations. Ключ — UUID в `Idempotency-Key`, область уникальности: companyId + userId + HTTP method + path + key. Запись хранится в PostgreSQL минимум 24 часа. Сервер резервирует ключ атомарно до побочного эффекта; результат и изменение данных фиксируются согласованно.

Повтор с тем же ключом и тем же каноническим JSON возвращает исходные код/тело/Location, не создавая новый ресурс. Для multipart сравниваются type и SHA-256 исходных байтов CSV (boundary и имя файла не учитываются). Другое тело с тем же ключом: 409 IDEMPOTENCY_KEY_REUSED. Если первый запрос ещё не завершён: 409 REQUEST_IN_PROGRESS, повторить тот же ключ через 1 секунду. Запросы, отклонённые до запуска из-за валидации, ключ не занимают. После 24 часов повтор не гарантирован: клиент сначала проверяет существующую операцию. PUT с version безопасен от повторного изменения, но повтор старой версии может вернуть 409.

## 4. Контракты операций

### POST `/auth/register` — Регистрация и создание организации

Атомарно создаёт компанию и пользователя. Email уникален глобально без учёта регистра. Вход в существующую организацию по companyId запрещён. Location указывает /api/v1/auth/me.

Тело: **Register**. Ответ: **201, AuthResult**.

### POST `/auth/login` — Вход

Неверные email и пароль дают одинаковый 401 INVALID_CREDENTIALS. Новый sid на каждую сессию.

Тело: **Login**. Ответ: **200, AuthResult**.

### POST `/auth/logout` — Выход из текущей сессии

Отзывает sid текущего JWT до exp. Другие сессии не затрагиваются; повтор с уже отозванным JWT даёт 401.

Тело: **отсутствует**. Ответ: **204, без тела**.

### GET `/auth/me` — Текущий пользователь и компания

Текущий пользователь и компания.

Тело: **отсутствует**. Ответ: **200, Profile**.

### GET `/companies/current` — Текущая организация

Текущая организация.

Тело: **отсутствует**. Ответ: **200, Company**.

## 5. Аналитика и рекомендации

### 5.1. Исходные данные

D = текущая дата UTC. Окно: [D−30; D−1] включительно, ровно 30 завершённых календарных дней. Сегодняшние продажи в расчёт не включаются. Дни без записей считаются нулевыми; отсутствие данных трактуется как отсутствие зарегистрированных продаж, а не доказанное отсутствие спроса.

Для каждого товара:

- S — сумма продаж за окно; A=S/30 — средние продажи в день.
- Q — последний текущий остаток.
- L — deliveryDays у вручную выбранного preferredSupplierId. Если поставщик не выбран: L=7, minOrder=1, price=null, supplierId=null, предупреждение SUPPLIER_NOT_SELECTED. Рекомендация может быть сформирована, но её бюджет неизвестен.
- B=7 — страховой запас в днях; H=30 — дополнительные дни покрытия после доставки.
- I — сумма quantities в закупках ORDERED для товара. Черновики и CREATED ещё не считаются подтверждёнными поставками.

### 5.2. Формулы и статусы

| Поле | Формула / правило |
|---|---|
| averageDailySales | A=S/30 |
| stockDays | Q/A при A>0, иначе null (не Infinity и не 0) |
| reorderPoint | A×(L+B) |
| targetStock | A×(L+H) |
| incomingQuantity | I |
| status=NO_SALES | A=0; проверяется первым |
| status=CRITICAL | A>0 и Q≤A×L |
| status=NEED_PURCHASE | A>0 и A×L<Q≤reorderPoint |
| status=NORMAL | A>0 и Q>reorderPoint |
| recommendedQuantity | При CRITICAL/NEED_PURCHASE: R=max(0,ceil(targetStock−Q−I)); если R>0, max(R,minOrder). При остальных статусах 0. |
| estimatedCost | recommendedQuantity×price при известной цене; иначе null |

Статус отражает физический запас, поэтому CRITICAL с recommendedQuantity=0 допустим: достаточный объём уже заказан. В MVP нет ожидаемой даты прибытия, поэтому приход не используется для улучшения статуса. При I>0 передаётся предупреждение INCOMING_NOT_DATED, а reason объясняет, что заказанный объём вычтен из количества, но дата прибытия неизвестна. minOrder — минимальная партия, а не кратность упаковки. Никаких округлений к кратности нет. Расчёты и сравнения выполняются до округления отображаемых полей. При недопустимо большом итоговом quantity задание завершается FAILED с NUMERIC_OVERFLOW; предыдущий снимок остаётся доступным.

Пример: S=60, A=2, Q=10, L=7, minOrder=20, price=100.00, I=0. stockDays=5, reorderPoint=28, targetStock=74, status=CRITICAL, quantity=64, cost=6400.00. Если I=70, status остаётся CRITICAL, quantity=0, cost=0.00.

reason — готовое русскоязычное объяснение с текущим остатком, средней продажей, сроком поставки, входящим объёмом и рекомендуемым количеством. Фронт показывает его как текст, не парсит для принятия решений. warningCodes — машинные признаки. NO_SALES обязательно включает одноимённое предупреждение и пояснение про данные за 30 дней.

### 5.3. Снимки и актуальность

Сервер увеличивает монотонную dataRevision компании при изменении товаров, остатков, продаж, предложений, выбранного поставщика или переходе закупки в/из ORDERED, включая RECEIVED. Неизменившийся upsert не повышает ревизию. Сервер автоматически планирует пересчёт после транзакции, объединяя частые изменения; после импорта — один пересчёт по завершении задания. На смене UTC-дня также планируется пересчёт. Предлагаемая задержка планирования — до 5 секунд; сами 30 секунд расчёта являются целевой метрикой PDF, не подтверждённым результатом тестирования.

Задание сохраняется в БД, выполняется одним worker через блокировку/lease с восстановлением после сбоя. Снимок читает согласованные данные одной ревизии; все его строки публикуются одной транзакцией. Старый снимок не удаляется при неудаче нового расчёта. Если во время расчёта пришли изменения, опубликованный результат имеет isStale=true, затем выполняется следующий расчёт. Снимки сохраняются в MVP без автоматического удаления.

isStale=true, если snapshot.dataRevision отличается от текущей или asOfDate не равна текущему UTC-дню. GET возвращает старые данные с этим признаком, а не выдумывает актуальные. Если снимка ещё нет — 409 ANALYTICS_NOT_READY. Фронт вызывает пересчёт, опрашивает job раз в секунду до COMPLETED/FAILED и повторяет чтение. После нового изменения завершившийся job не гарантирует isStale=false: проверка обязательна.

Для пагинации рекомендаций фронт сохраняет snapshot.id первого ответа и передаёт snapshotId для следующих страниц. Иначе между страницами может смениться снимок. recommendationId принадлежит одному неизменяемому снимку. Перед созданием закупки сервер под блокировкой ревизии проверяет, что он последний и актуальный. Изменение предпочтительного поставщика требует пересчёта; альтернативно можно создать закупку вручную без recommendationId, используя текущие предложения.

### 5.4. Dashboard

Все значения из одного снимка:

- totalProducts: все товары.
- criticalProducts: число CRITICAL, даже если закупка уже заказана.
- productsToPurchase: число товаров с recommendedQuantity>0; **включает критические**.
- potentialStockouts: число товаров с A>0 и stockDays<L (строго меньше); при L=0 это 0.
- recommendedBudget: сумма известных estimatedCost для recommendedQuantity>0, минимум "0.00".
- unpricedRecommendations: число рекомендаций с quantity>0 и price=null. Если больше нуля, бюджет неполный — фронт обязан это подписать.
- criticalItems: первые 10 CRITICAL; recommendations: первые 10 с quantity>0. Порядок как у списка рекомендаций. Эти массивы могут пересекаться, их счётчики не складываются.

## 6. Закупки и изменение складского остатка

Допустимые переходы:

| Текущий статус | Разрешённый следующий | Изменение остатка |
|---|---|---|
| DRAFT | CREATED, CANCELLED | Нет |
| CREATED | ORDERED, CANCELLED | Нет |
| ORDERED | RECEIVED, CANCELLED | При RECEIVED прибавить quantity каждой позиции |
| RECEIVED | Нет | Нет |
| CANCELLED | Нет | Нет |

Повтор текущего статуса при актуальной version — 200 без изменений. Любой другой переход — 409 INVALID_STATUS_TRANSITION. Отмена ORDERED означает, что поставка не состоялась: частичные поставки и возвраты не моделируются. После CREATED состав/цены неизменяемы. CREATED→ORDERED не отправляет заказ внешнему поставщику автоматически — это учётный статус.

POST /purchases и PUT состава фиксируют цену, deliveryDays и minOrder из текущего предложения. Изменения прайса впоследствии не меняют закупку. Для DRAFT→CREATED сервер проверяет наличие позиций и допустимость сохранённых значений, но не переоценивает их молча. Если нужен новый прайс, пользователь повторно сохраняет DRAFT через PUT. Сумма строки = price×quantity; totalCost = сумма строк. Все позиции принадлежат поставщику и текущей компании, повторяющиеся productId запрещены (422 DUPLICATE_PRODUCT). Пустая закупка недопустима. Клиент не передаёт status, price, totalCost, companyId, createdByUserId или receivedAt при создании.

RECEIVED выполняется одной транзакцией: блокировка закупки → проверка version и статуса → блокировка inventory в порядке productId → проверка переполнения → увеличение quantities и versions → запись receivedAt и статуса → повышение ревизии. Ошибка любой позиции откатывает всю операцию. Конкурентный импорт/ручное обновление используют те же блокировки. Проверка version предотвращает повторный приход даже при потере HTTP-ответа. После 409 клиент получает закупку: если она RECEIVED, повторять приход не нужно.

Продажа через API или CSV **не уменьшает inventory**, поскольку исходник описывает отдельные выгрузки продаж и остатков. Иначе загрузка обоих файлов привела бы к двойному списанию. Импорт inventory устанавливает абсолютное значение на момент обработки; пользователь должен загружать актуальный файл, а не старый снимок. Устаревание внешнего CSV автоматически определить невозможно — в MVP нет временных меток источника.

## 7. CSV-импорт

POST /imports: поле type = PRODUCTS / INVENTORY / SALES / SUPPLIERS, поле file — файл. Фронт не выставляет multipart boundary вручную. Ответ 202 возвращает задание; фактическое завершение видно только через GET /imports/{id}.

Формат: UTF-8, допустим BOM; разделитель запятая; первая строка — обязательные заголовки; переводы LF/CRLF; значение с запятой заключается в двойные кавычки, кавычка экранируется двойной кавычкой. Десятичный разделитель — точка. Заголовки чувствительны к регистру; порядок произвольный, лишние/дублирующиеся/пропущенные обязательные столбцы запрещены. Полностью пустые строки пропускаются и не учитываются. До 10 000 непустых строк данных и 10 MiB (10 485 760 байт). `row` — номер логической CSV-записи, включая заголовок; перенос внутри кавычек не увеличивает номер записи.

| type | Обязательные столбцы | Необязательные | Ключ / действие |
|---|---|---|---|
| PRODUCTS | sku,name | category | SKU внутри компании. Новый товар + inventory=0; существующему заменить name/category. preferredSupplierId не менять. |
| INVENTORY | sku,quantity | — | Найти существующий товар; заменить абсолютный quantity. Новые товары не создавать. |
| SALES | sku,sale_date,quantity | — | (товар, дата). Создать/заменить дневную сумму. Не прибавлять и не менять inventory. |
| SUPPLIERS | supplier_name,sku,price,delivery_days,min_order | — | По нормализованному имени создать/найти поставщика, затем создать/обновить предложение для существующего SKU. Не выбирать поставщика автоматически. |

Отсутствующий столбец category или пустая ячейка очищают категорию в PRODUCTS. В остальных обязательных столбцах пустые значения недопустимы. Нулевые quantity/price разрешены; min_order≥1, delivery_days от 0 до 365. Дата продаж не позже сегодня UTC. SKU неизвестен — ошибка строки, кроме PRODUCTS. Один SKU в разных компаниях — разные товары. Изменять имя поставщика через CSV нельзя: новое имя создаёт нового поставщика; переименование выполняется PATCH.

Дубли ключа внутри файла: первая встретившаяся строка резервирует ключ, последующие дают DUPLICATE_ROW, даже если первая содержала другую ошибку. Порядок обработки совпадает с порядком строк. Структурно корректные файлы обрабатываются частично: одна строка — одна транзакция; если она невалидна, никаких её изменений нет (включая создание поставщика). Для SUPPLIERS строка считается created, если создано предложение, updated — если изменено предложение; создание самого поставщика отдельно в счётчик не добавляется. Поэтому все счётчики отражают **строки**, не число изменённых таблиц.

В конце: processedRows = totalRows = createdCount + updatedCount + unchangedCount + errorCount. Для INVENTORY createdCount всегда 0: складская строка создаётся вместе с товаром. Повтор неизменившегося значения — unchangedCount, версии не повышаются. Для SALES и PRODUCTS счётчики соответствуют созданию/изменению основной записи. Для ошибок строк отдаётся одна первая ошибка по порядку столбцов; полный отчёт доступен через пагинацию /errors.

Статусы: QUEUED→RUNNING→COMPLETED (нет ошибочных строк), COMPLETED_WITH_ERRORS (есть ошибочные строки, в том числе все строки ошибочны) или FAILED (структурная/системная ошибка). В RUNNING totalRows может быть 0 до завершения предварительного разбора. Невалидная структура, кодировка или более 10 000 строк обнаруживаются при предварительном разборе: FAILED, error.code=INVALID_CSV/CSV_ROW_LIMIT, без применения строк. Размер свыше лимита — 413 сразу; неподдерживаемый media type — 415. Пустой файл без заголовка — FAILED INVALID_CSV; корректный заголовок без данных — COMPLETED с нулевыми счётчиками.

При системной ошибке после части обработки уже подтверждённые строки остаются применёнными; status=FAILED, счётчики отражают обработанную часть, `error` объясняет сбой. Повтор того же idempotency key возвращает тот же job. Для повторной обработки файла нужен новый ключ; абсолютный upsert предотвращает повторное начисление продаж/остатков. Конкурентные импорты одной компании выполняются последовательно. Ручные изменения разрешены; строка импорта применяет абсолютное значение под блокировкой и может заменить более раннее ручное значение. Фронт должен показывать активный импорт, а не обещать защиту его данных через отсутствующую в CSV version.

Примеры отдельных файлов:

```csv
sku,name,category
TEA-001,Чай зелёный,Напитки
```

```csv
sku,quantity
TEA-001,10
```

```csv
sku,sale_date,quantity
TEA-001,2026-10-24,2
```

```csv
supplier_name,sku,price,delivery_days,min_order
ООО Поставщик,TEA-001,100.00,7,20
```

Порядок первичной загрузки: PRODUCTS → INVENTORY / SALES / SUPPLIERS → ручной выбор preferredSupplierId → пересчёт → рекомендации. Задания импорта и результаты сохраняются в БД; исходные файлы — в постоянном файловом хранилище/volume, доступном worker. После рестарта записи с истёкшим lease возобновляются с последней подтверждённой строки; checkpoint и применение строки фиксируются атомарно.

## 8. Ошибки

Единый формат всех JSON-ошибок:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Проверьте данные запроса",
  "traceId": "req-7f68e5",
  "details": [
    {"field": "items[0].quantity", "code": "MIN_ORDER_NOT_MET", "message": "Минимальная партия — 20"}
  ]
}
```

`details=[]` для общей ошибки. Поле field содержит путь JSON, имя query-параметра или заголовка. Stack trace, SQL, хеши паролей и внутренние исключения не возвращаются. traceId используется для поиска серверного лога. Ошибки CSV в /errors имеют отдельную схему ImportError, а фатальная ошибка job — Error или null. HTTP 200 при чтении FAILED-job означает успешное чтение задания, а не успешный импорт.

| HTTP | code | Действие фронта |
|---|---|---|
| 400 | BAD_REQUEST | Исправить синтаксис JSON/параметра/заголовка |
| 401 | UNAUTHORIZED, TOKEN_EXPIRED, TOKEN_REVOKED, INVALID_CREDENTIALS | Очистить сессию либо показать ошибку входа |
| 403 | FORBIDDEN | Показать отсутствие разрешения; в модели равных прав редкий защитный случай |
| 404 | RESOURCE_NOT_FOUND | Показать отсутствие ресурса, не раскрывать чужую компанию |
| 409 | EMAIL_ALREADY_EXISTS, SKU_ALREADY_EXISTS, SUPPLIER_ALREADY_EXISTS | Исправить уникальное значение |
| 409 | VERSION_CONFLICT | Перечитать ресурс, не перезаписывать молча |
| 409 | RESOURCE_IN_USE, INVALID_STATUS_TRANSITION | Показать недопустимость операции |
| 409 | ANALYTICS_NOT_READY, STALE_RECOMMENDATION | Дождаться/запустить пересчёт, обновить данные |
| 409 | IDEMPOTENCY_KEY_REUSED, REQUEST_IN_PROGRESS | Не менять тело повтора; дождаться результата |
| 413 | FILE_TOO_LARGE | Уменьшить CSV |
| 415 | UNSUPPORTED_MEDIA_TYPE | Отправить правильный формат |
| 422 | VALIDATION_ERROR, DUPLICATE_PRODUCT, MIN_ORDER_NOT_MET, NUMERIC_OVERFLOW | Показать ошибки полей |
| 429 | TOO_MANY_REQUESTS | Соблюдать Retry-After |
| 500 | INTERNAL_ERROR | Показать traceId; запись повторять только безопасным способом |

При семантических ошибках полей верхний code обычно VALIDATION_ERROR, конкретный код в details. В таблице также разрешены конкретные верхние коды для одной бизнес-ошибки. В CSV дополнительно используются UNKNOWN_SKU, DUPLICATE_ROW, INVALID_VALUE, INVALID_DATE; фатально INVALID_CSV, CSV_ROW_LIMIT, INTERNAL_ERROR. Для всех ошибок изоляция компании проверяется до возвращения деталей чужого ресурса.

## 11. Изменения модели относительно ER

ER из PDF — основа, но недостаточна для всех описанных операций. Предлагаемые дополнения для реализации контракта:

1. product: preferred_supplier_id nullable, updated_at, version; unique(company_id,sku). Проверка связи с предложением поставщика этой же компании.
2. inventory: unique(product_id), version; количество неотрицательно. Одна строка автоматически на каждый товар.
3. sale: unique(product_id,sale_date), version, created_at; quantity≥0. Разные каналы продаж предварительно агрегируются перед импортом.
4. supplier: version, нормализованное имя с unique(company_id,normalized_name). supplier_product: unique(supplier_id,product_id), version, created_at.
5. purchase: version, updated_at, received_at. purchase_item: recommendation_id nullable, снимки delivery_days/min_order; существующее price — снимок цены. Уникальность (purchase_id,product_id).
6. purchase_recommendation: snapshot_id, supplier_id nullable, price nullable, incoming_quantity, warning_codes и необходимые исходные показатели. Неизменяемая запись принадлежит снимку; текстовые sku/productName сохраняются, чтобы удаление товара не ломало историю снимка.
7. Новые таблицы/эквивалентные структуры: analytics_snapshot, calculation_job, import_job/import_row_error и checkpoint, idempotency_record, revoked_session, ревизия данных компании. Они постоянные и company-scoped.
8. Ограничения companyId для всех составных связей: SQL-ограничения, где возможно, плюс сервисная проверка. FK без проверки компании недостаточно.

В API сохраняются названия сущностей PDF, но JSON — самостоятельные DTO: нельзя возвращать JPA-сущности целиком. Пароли, внутренние связи и lazy-прокси в ответ не попадают. Отдельный API изменения организации и управление пользователями не добавляются без отдельного требования.

## 12. Приёмка и работа команд

Это критерии будущей реализации, а не утверждение о пройденных тестах сервера:

| Сценарий | Ожидаемый результат |
|---|---|
| Пользователь A читает/изменяет товар, поставщика, job или закупку B | 404, отсутствие изменений и утечки |
| Чужой supplierId или recommendationId в теле | 404, вся транзакция отменена |
| Повтор SKU в компании | 409; тот же SKU в другой компании допустим |
| Запись отрицательного остатка/дробного quantity | 422 |
| Два изменения с одной version | Одно успешно, другое 409 |
| Повтор POST покупки с тем же ключом | Тот же ID и 201, без дубля |
| Тот же ключ с другим телом | 409 IDEMPOTENCY_KEY_REUSED |
| Двойной/конкурентный RECEIVED | Один приход; второй запрос не увеличивает склад |
| Импорт одинаковых SALES дважды | Продажи не удваиваются, второй результат unchanged |
| CSV с одной ошибочной строкой | Остальные строки применены, отчёт содержит номер и причину |
| CSV с неверными заголовками | FAILED, нет изменений |
| A=0 | NO_SALES, stockDays=null, quantity=0 |
| Пример S=60,Q=10,L=7 | CRITICAL, quantity=64, cost=6400.00 при price=100.00 и I=0 |
| Заказанного объёма хватает | quantity=0, физический статус может остаться CRITICAL |
| Поставщик не выбран | price/cost=null, предупреждение, бюджет помечен неполным |
| Данные изменились после расчёта | isStale=true; покупка по старой рекомендации → 409 |
| JWT после logout | 401 на любом экземпляре backend |
| Рестарт в середине импорта/прихода | Нет потери данных, дублирования строки или повторного прихода |

Целевые метрики из PDF: 95% обычных REST-запросов ≤2 с; Dashboard ≤3 с при 10 000 товаров; импорт ≤30 с на 10 000 строк; расчёт рекомендаций ≤30 с на 10 000 товаров; доступность ≥99% в месяц вне планового обслуживания. Для async измеряется время от приёма job до терминального статуса, а не только быстрый ответ 202. Подтверждать нагрузочным тестированием; факт наличия контракта эти показатели не доказывает.

Frontend: загрузить openapi.yaml в используемый генератор/редактор OpenAPI, создать типы DTO и mock-ответы; экраны привязывать к operationId, enum и описанным правилам. Backend: реализовать DTO и валидацию, затем транзакции, tenant-проверки и state machine; HTTP-интеграционные тесты должны проверять фактические ответы против контракта. Оба файла хранить рядом в репозитории, например docs/api/API.md и docs/api/openapi.yaml. Изменение имени поля, типа, обязательности или enum требует совместного изменения контракта до изменения потребителей.

Для первой сквозной реализации: auth/company → products/inventory → sales → suppliers/offers → import → calculations/recommendations/dashboard → purchases. Набор данных для примера должен явно содержать 60 продаж за расчётные 30 дней. Указанные IDs и JWT в примерах иллюстративны; реальный сервер возвращает собственные значения.
