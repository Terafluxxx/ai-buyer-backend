# Этап: товары, остатки и продажи

Реализованы 11 операций: GET/POST products, GET/PATCH/DELETE products/{id}, GET inventory,
GET/PUT products/{id}/inventory, GET sales, PUT products/{id}/sales/{date}, GET sales/summary.

Все запросы ограничиваются companyId проверенного JWT. Чужие ID дают 404, включая фильтры.
Параметры и JSON валидируются; PATCH различает отсутствующее поле и null.
SKU уникален внутри компании, продажи агрегируются по дню. Продажи не меняют остаток.
No-op не меняет version/dataRevision. При изменении версия и ревизия увеличиваются атомарно.

Для сериализации записей используется блокировка строки компании. Это простая корректная база
для будущей проверки актуальности рекомендаций; она ограничивает параллельную запись внутри компании.
Пагинация выполняется в SQL. Query q ищет буквальную подстроку без интерпретации % и _ как wildcard.

## Границы этапа

Модуля поставщиков ещё нет: ненулевой preferredSupplierId пока не может быть назначен (404),
при создании ненулевое значение запрещено контрактом (422).
После появления предложений необходимо добавить FK и проверку связи supplier/product.
Удаление защищает остатки и продажи; после добавления закупок требуется защита их истории.
Ревизия данных сохраняется, но автоматическое планирование аналитики будет реализовано с постоянными заданиями.

## Проверки

HTTP-тесты проверяют tenant isolation, конфликты версий, отсутствие списания склада продажами,
no-op, очистку category через null, SKU, пагинацию, удаление и строгие параметры.
Локальная среда: Java 17/ECJ и H2 PostgreSQL mode. CI: Java 21/PostgreSQL 17.
